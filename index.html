Measured on this chain: WETH.permit cannot be sent as an L2 transaction at all. The pool only accepts an L2 gas limit pinned to the eth_estimateGas answer (87378 for this call) while the call needs about 104000 gross, so it always ends out of gas - and every limit between 100k and 112k is refused outright. The same permit inside an L1 delayed message is admitted (95000 and 110000 both executed). Step 1 is therefore the only permit route: one mainnet ticket to the delayed inbox, message gas limit 110000, which the sponsor's L2 alias executes minutes later at its own L2 gas. The calldata stays cheap - full owner balance and a deadline rounded to whole millions (trailing zero bytes, no signature grinding).

The permit's spender is the sponsor, not multicall3: transferFrom requires msg.sender == spender, and the pull is a separate transaction sent by the sponsor. multicall3 is only the wrapper callee, there to make the message a selector the policy admits (0x82ad56cb, aggregate3, exactly one call, allowFailure = true so an inner revert still returns instead of burning the message). Steps 2 and 3 are ordinary L2 transactions from the sponsor: they estimate first, walk the narrow gas ladder and land in seconds. Only the allowance bridges the two: the pull arms when allowance(owner, sponsor) is above zero, i.e. once the inbox has run the permit.

Fallback: - the same permit at a plain L2 gas limit, worth a try only if the pool ever starts admitting it.
